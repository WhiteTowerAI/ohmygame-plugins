# 进化流程

一代 = 生成 → 对抗评审 → 打分选择 → 记录。插件和游戏两条线并行。

## 文件

- `GOAL.md` 目标和停止条件；`RUBRIC.md` 评分规则；`CONTEXT.md` OhMyGame 现状和插件 API。
- `EVIDENCE.md` 证据库，每条有编号（E1、E2…）、数据和来源。来自 `../reports/游戏开发真实痛点调研.md` 和 `../research_notes/游戏开发真实痛点调研/`。
- `pool/plugins.md`、`pool/games.md` 当前种群：每个想法有 ID、谱系（来自哪一代、由谁变异或合并）、最新得分、状态（存活 / 淘汰 / 终选）。
- `generations/gen-N-<plugins|games>-proposals.md` 生成者的提案；`gen-N-<...>-review.md` 评审结果；`generations/gen-N-summary.md` 本代小结。
- `FINAL.md` 终选结果。

## 每一代

1. **生成**（每条线一个生成者）
   - 第 1 代：从证据库出发，每条线提 12–15 个候选，每个必须写明解决的需求、引用的证据编号。
   - 之后各代：拿上一代存活者和评审意见，做三件事：修正致命问题、合并相近的想法、补 3–5 个针对证据库里**还没被覆盖的高频痛点**的新候选。淘汰的不能原样复活。
2. **对抗评审**（每条线一个评审，和生成者独立）
   - 先核对证据：引用的编号是否真的支持这个说法，有没有夸大。
   - 再找致命问题，按 `RUBRIC.md` 打分，每分写理由。
   - 指出证据库里频率高但没被任何候选覆盖的痛点。
3. **选择**（协调者）
   - 有致命问题且无法修正的淘汰；按得分保留前 8–10 名进入下一代。
   - 更新 `pool/`，写 `gen-N-summary.md`：前 5 名、变化、覆盖缺口。
4. **停止判断**：见 `GOAL.md`。

## 防止跑偏

- 生成者和评审不是同一个 agent，评审看不到生成者的推理过程，只看提案。
- 分数必须引用证据编号；没有证据的维度最多 2 分。
- 每代记录覆盖了哪些高频痛点，防止所有想法挤在一个方向。
