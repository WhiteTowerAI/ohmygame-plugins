## P1-01 试玩验收官（proof-of-play）

**用户与场景**：用 OhMyGame 让 Agent 加功能的创作者，尤其做物理、实时动作、3D 的人。Agent 改完代码说"我测过了，运行完美"，人一打开就发现角色飞出地图、按钮点不了、画面全黑。痛点在 Agent 交付的那一刻：它自己写的代码、自己判断对错，人要么全信要么每次都手动复查。

**证据**
- E41（弱，轶事）：物理游戏开发者两张截图之间角色"shot off the map into deep space"，接了 step API 后仍不时收到 "I tested it and it works perfectly!"；只看代码的测试会编出不存在的选择器；对照规范验证已知功能最省时，每个功能后跑回归"pretty cheap"。直接对应要解决的场景。
- E42（弱，轶事）：Godogen 另设一个只看截图、不看代码的视觉 agent，因为编码 agent "biased toward its own output"，抓到了 z-fighting、悬浮物体、物理爆炸。说明"独立评审"这条路走得通。
- E36（弱，厂商 n=615）：47% 用 AI 做试玩与平衡。这是唯一的比例数据，但属厂商调查。
- E23（强，论文）：测试问题占复盘 5%，有子类 "Scope too big to test properly"，且可能被低估。
- E44（弱）："A jump that feels floaty compiles fine and reads fine"：代码层面看不出运行时问题。
- 证据整体判断：痛点频率**没有强定量数据**，主要是 AI 原生的新痛点，轶事多但方向一致。它的分量来自 OhMyGame 自己的核心承诺（"Agent 在实时预览里亲自试玩"）：Agent 误报一次，用户对整个产品的信任就掉一截。

**做什么（MVP）**
1. **回合级"未验证"提示**：`tool.afterCall` 记录每次 `game_use` 调用和结果，`turn.completed` 拿到本轮改动的文件。如果改了游戏代码或素材，最后一次改动之后却没有任何运行时证据（截图、snapshot、录屏），就弹 `danger` toast："本轮改了 N 个文件，改动后没有运行验证"，并在面板记一笔。
2. **独立视觉评审**：插件用 `capabilities.game` 自开会话，按设计文档里的验收条目（如"按空格角色起跳并落回地面"）执行动作；有 `step` 时按固定步长逐帧截图，没有时按时间间隔截图。截图交给 `capabilities.models`（用户配置的多模态模型），评审提示词**不含任何代码**，只给验收条目和画面，输出结构化结论：通过 / 不通过 / 看不清，附异常类型（离开画面、悬浮、穿模、全黑、UI 遮挡、文字溢出）。
3. **状态不变式**：在 `playtest/invariants.json` 里声明不变式（玩家坐标在关卡包围盒内、速度不超过上限、HP 不为负、实体数量不爆涨）。插件逐帧读 `snapshot`，违反即记下帧号、前后截图和状态差异。专门针对"两张截图之间飞走"这类截图抽样漏掉的问题。
4. **证据报告面板**：每次验收生成一页报告，包括逐帧截图条、不变式曲线、评审结论和复现步骤；提供"把失败项发给 Agent 修"的命令（填进 Composer）。
5. **Agent 工具 `verify_change`**：Agent 改完后自己调用，返回上面的结论；配套的 instructions 要求说"完成"之前先调用它。

**和已有功能的区别**：`game_use` 是 Agent 的手和眼，判断仍由写代码的同一个 Agent 做；web-game-studio 的 game-playtest 是一份做法说明；Game Tests 是开发者或 Agent 写的脚本化回归测试，断言由写代码的一方决定。本插件补三件它们没有的事：**和写代码的 Agent 隔离的评审**、**逐帧不变式监控**、**回合级"未验证"提示**。Game Tests 合并后，可以把通过验收的条目导出成它的回归用例，两者互补。

**用到的能力 / 宿主缺口**
- 用到：`capabilities.game`（open/act/capture/captureFrame/recordStart）、`capabilities.models`（图片输入）、hooks `tool.afterCall`、`turn.completed`、`files.changed`；Agent 工具；面板；instructions。
- 缺口 1：`turn.completed` 只能弹 toast，不能把"未验证"直接退回给 Agent 让它继续。需要宿主提供回合结束时追加一条系统提示的接口（类似 stop hook）。`capabilities.sessions` 的 `send` 能做到，但要求全局授权、跨项目读对话，权限过大，不作为方案。
- 缺口 2：模型调用限额是每插件 30 次/分钟、3 并发，逐帧评审要抽样，比如只评关键帧和不变式报警帧。
- 缺口 3：需要确认插件会话的 `act` 能否调用测试桥的 `step`/`snapshot`（文档说 `game_use` 的动作包含测试桥，插件会话应与之一致，要实测）。

**怎么衡量成功**
- 埋入已知 bug 的基准集（在 5–10 个示例游戏里人为加入飞出地图、按钮失效、黑屏等 30 个缺陷）：检出率、误报率。
- 用户侧：改了代码的回合里带运行时证据的比例；"Agent 说修好了但没修好"的人工反馈（返工回合数）下降。
- 每次验收的平均耗时和 token / 模型调用数。

**风险与最弱点**
- **最弱点：证据几乎全是轶事**（E41、E42、E44），唯一的比例 E36 是厂商调查。评审很可能在"需求频率"和"证据强度"上压分。
- 视觉模型自己也会误判（把正常的特效判成异常），误报多了用户会关掉。需要"看不清"这一档，并允许人工标注后不再报警。
- 不变式要有人写，没有测试桥的游戏只能走纯截图，能力打折扣。

## P1-02 数值平衡实验室（balance-lab）

**用户与场景**：做肉鸽卡牌、放置/增量、塔防、回合策略的 1–3 人团队。调参面板能实时改数值，但"这张卡是不是太强""第 20 分钟会不会无事可做""第 5 关是不是难度断崖"，靠手玩几局看不出来，找人试玩又慢又少（见 P1-03）。

**证据**
- E27（强，论文，25,534 个问题）：balance 是问答站平均浏览最高的标签之一，也是得分/收藏高的标签。平衡是开发者反复查的问题。
- E13（强）：根因里 Lack of fun 27 次、Game design complexity 23 次。
- E36（弱，厂商）：47% 用 AI 做试玩与平衡；agent 用途中"动态平衡" 38%。
- E41（弱）：有开发者从浏览器测试转向"millions of simulated games headless"的无头蒙特卡洛模拟。
- E93、E95（中）：命中率和中位收入较高的品类（肉鸽卡牌 5.1%、放置 2.79%、塔防）恰好都是数值驱动、适合模拟的类型。
- 判断：需求本身有强证据（E27、E13），"用模拟解决"的证据弱。

**做什么（MVP）**
1. **模拟接口约定**：`init(seed, params)`、`legalActions(state)`、`apply(state, action)`、`isOver(state)`、`metrics(state)`。用 SDK 写的多人规则直接复用 `simulateRoom`（确定性时钟和种子已有），单机游戏由 Agent 按 skill 从现有逻辑里抽出纯函数模块。
2. **机器人策略库**：随机、贪心（一步前瞻）、轻量 MCTS，以及"原型策略"（只拿攻击卡、只升级产出、只造某种塔），用来暴露必胜套路。
3. **批量运行**：原生代码用 worker_threads 跑 1k–100k 局，esbuild 打包项目模块。输出胜率按策略分布、单局时长分布、卡牌/道具"选取率 × 胜率"矩阵、放置类的"距下一次升级的等待时间"曲线（标出超过 X 分钟的空档）、逐关通过率。
4. **参数扫描**：读 `tuning.json` 的数值和范围，做一维/二维扫描，出热力图；把建议值写成一条"待确认的改动"，人点确认后才写入 `tuning.json`。
5. **面板**：图表 + "疑似问题"列表（统治策略、无效卡、节奏空档、难度断崖），每条附可复现的种子，点一下就能用 `game.open` 带种子进游戏亲手看。

**和已有功能的区别**：调参面板是单局实时手调，不出统计；`simulateRoom` 是给多人规则写单元测试的底座，没有机器人、批量运行和统计；P1-01 验证"有没有坏"，本插件回答"数值是否合理"。外部有 Machinations 等可视化经济建模工具，但它们要求另画一遍模型，不跑游戏自己的代码。

**用到的能力 / 宿主缺口**
- 用到：原生代码（worker_threads、esbuild）、面板（图表、`ui.projectModules` 导入项目逻辑模块做小规模交互模拟）、Agent 工具 `run_balance_sim`、skill（如何抽出纯逻辑）、`capabilities.game`（带种子复现）。
- 缺口：无硬缺口。软缺口：调参面板如果能接收"建议值"并显示对比，体验会更好；目前只能直接改文件或经 Agent 改。

**怎么衡量成功**
- 目标品类项目中用过的比例；每次模拟后被采纳的数值改动数。
- 模拟发现的问题里，后来被真人试玩（P1-03）或评论证实的比例。
- 从"想验证一个数值改动"到拿到结论的时间（目标：分钟级）。

**风险与最弱点**
- **最弱点：只对规则能和画面分离的游戏有效**。实时动作、物理类基本用不上，Agent 抽纯逻辑也可能抽错，模拟结果因此失真。
- 机器人不是人：能找出退化策略和节奏空档，但不能证明"好玩"，宣传时不能承诺这一点。
- "AI 用于平衡"的比例数据只有厂商调查（E36）。

## P1-03 真人试玩回路（playtest-loop）

**用户与场景**：游戏已经能玩，想知道陌生人玩起来怎样的个人开发者。发链接给群友，最后只收到几句"挺好玩"；不知道多少人加载完就走了、卡在第几关、哪里看不懂。Poki 的试玩录像只对进了 Poki 流程的游戏开放。

**证据**
- E21（强，论文 n=13 定性）：独立开发者试玩的五个难点：时间和钱不够、招不到有代表性的玩家、选方法、分析数据（"even something as simple as recording the screen and the player and the input all at the same time is not something that everyone can do"）、处理反馈时对单条评论反应过度；翻"2–3 days' worth of Discord messages"很耗时；难写无偏的问题。
- E22（强，论文 n=10）：受测试者数量和代表性限制。
- E24（中）：GMTK 2024 作品评分中位数只有 14 个；有网页版的 jam 作品平均约 5 个评分，没有的约 1 个。反馈本来就稀缺，链接即玩才拿得到。
- E26（强，官方）：Poki 上传后几分钟内给 10–20 段真人录像；Cannon Clash 根据试玩删掉了开场动画。说明"录像 + 快速迭代"有效，平台已把它做成基础设施。
- E8（弱）：LORT 做过 500 人试玩后在 Next Fest 突破。
- E13（强）：论文作者建议"多试玩"。

**做什么（MVP）**
1. **试玩构建**：发布菜单里的"生成试玩链接"命令（`build: "web"`），给构建注入一个很小的采集模块：加载进度、首次输入、关卡/事件（游戏通过一个 `track()` 调用上报，Agent 按 skill 接好）、退出位置、报错，以及退出或死亡前约 20 秒的低帧率画布片段（`canvas.captureStream` + MediaRecorder，不需要系统权限）。首屏给出明确的同意提示，不同意就只记匿名漏斗。
2. **结束问卷**：2–3 个按 E21 原则写的无偏问题模板（"你最后在做什么？""哪一刻想退出？"），不问"好不好玩"。
3. **面板**：漏斗（打开 → 加载完 → 首次输入 → 1 分钟 → 第 2 关 → 通关）、退出点和死亡点热区、片段墙（按"卡点"聚类排序）、报错列表。
4. **反馈聚类**：拉取社区评论（公开接口）、导入问卷回答、粘贴 Discord/飞书消息，用 `capabilities.models` 聚成"问题 → 提到人数 → 代表原话"，每条标注样本量，避免对单条意见过度反应。可一键把某个问题发给 Agent。
5. **玩法 A/B**：同一链接按比例分到两个构建（例如有无开场动画、两种跳跃手感），面板对比漏斗和时长，样本不足时明说"差异不显著"。

**和已有功能的区别**：社区页只有浏览、点赞、评论；`game_use` 是 AI 在玩；P1-01/P1-02 是机器验证。本插件是 OhMyGame 里唯一面向**真人**数据的环节。外部有 GameAnalytics 等 SDK，但它们只出指标，不带画面片段，不做反馈聚类，也不接 Agent 修改闭环。

**用到的能力 / 宿主缺口**
- 用到：`build: "web"` 原生命令、`project.publish` 菜单项、面板（`net.fetch`）、`capabilities.models`、Agent 工具、skill。
- **缺口 1（关键）**：需要地方收数据。`capabilities.network` 的主机写死在 manifest 里，用户自填的后端（Supabase、R2 等）无法动态声明。两条路：(a) 宿主在 OhMyGame Cloud 给已发布游戏开一个"试玩事件 + 短片段"收集接口（社区已有评论和浏览数，延伸自然）；(b) 插件作者托管一个收集服务。(a) 更好，隐私责任也更清楚。
- 缺口 2：隐私合规（GDPR、国内个人信息保护法），同意文案和数据保留期由宿主统一定更稳妥。

**怎么衡量成功**
- 每个试玩链接收回的有效会话数；发布前收到 ≥10 个真人会话的项目比例。
- 从分享链接到第一份聚类报告的时间。
- 来自试玩报告、被 Agent 修掉的问题数；A/B 实验做完并采纳的次数。

**风险与最弱点**
- **最弱点：依赖宿主或第三方后端**，否则做不出 MVP。
- 招人难（E21 第 2 点）本插件只解决一半：它让每个玩家的数据更值钱，但不负责找来玩家。可以和社区、飞书机器人联动，但不承诺找人。
- 录屏片段的大小和流量成本要控制（只在退出或死亡时上传）。

## P1-04 网页上线体检（web-launch-doctor）

**用户与场景**：游戏在桌面预览里一切正常，准备发到门户、小游戏或分享到手机。实际情况是：首包 20 MB 加载十几秒；手机竖屏时按钮在屏幕外；iPhone 上没声音；Safari 无痕模式下存档报错；贴图一多 iOS 页面被杀掉重载。这些问题都很机械，但不查清楚就会被驳回或流失玩家。

**证据**
- E53（强，官方）：每多 1 MB 流失几个百分点玩家；Poki 首包建议 5 MB / 总计 8 MB；Cannon Clash 用 Draco、Basis、合图、减碰撞面，做到 2.4 MB / 76 个请求，进入游戏转化 81%。
- E65（弱，Poki 委托调查 n=2,000 名玩家）：手机上 46% 因加载时间、28% 因下载大小放弃过游戏。
- E56（强）：CrazyGames 初始下载 ≤50 MB，上手机首页须 ≤20 MB；iOS 要在 touchend 里 resume AudioContext；iOS 和低内存安卓用 DPR 1；Safari 跑不了就在 Safari 下架。
- E62（强）：YouTube Playables 初始包 <30 MiB（建议 <15），单文件 <30 MiB（建议 <512 KiB），≤8,000 个文件。
- E82（强）：微信/抖音主包 4 MB，总计 30 MB。
- E54（强）：竖屏优先，注意刘海和平台叠加 UI；移动 Safari 会清 iframe 存储；localStorage 须包 try/catch。
- E67（弱）：iOS Safari 按内存预算杀页面，WebGL context 丢失，WASM 编译超限。E68（强）：自动播放限制，iframe 要 `allow="autoplay"`。
- E66（弱，单案例）：AI 写的 Three.js 游戏上 CrazyGames 前补了六处：静态构建、相对路径、外部字体、删无用素材（20.5→12.4 MB）、横竖屏按钮位置。
- E27（强）：aspect-ratio 是问答站平均浏览最高的标签（4,483）。

**做什么（MVP）**
1. **包体报告**：`build: "web"` 命令 + `build.completed` 钩子。分析首包与懒加载部分（解析入口 HTML、JS import 图和预加载清单），按目标平台配置文件（Poki、CrazyGames 手机/桌面、Playables、微信/抖音主包、社区）对照预算，列出最大文件、未被引用的素材、外部请求（Google Fonts、CDN）、绝对路径。
2. **一键优化**（每项单独可撤销，走插件写入的检查点）：GLB 用 gltf-transform 做 Draco/meshopt 压缩和贴图缩放；图片转 WebP/AVIF 或合图；音频转 OGG + M4A 双格式并降码率（复用宿主的 ffmpeg）；字体子集化；外部字体和库改成本地打包。
3. **移动端规则检查**（静态扫描 + 运行时验证）：AudioContext 在手势里 resume、localStorage try/catch、`visibilitychange` 暂停、DPR 上限、`user-select: none` / `touch-action`、WebGL context lost 处理、安全区 CSS。运行时用 `capabilities.game` 依次以竖屏/横屏、小屏尺寸打开游戏并截图，交给视觉模型判断"关键按钮是否在可视区内、文字能否看清"。
4. **iOS 内存估算**：按贴图解码尺寸（宽 × 高 × 4 × mip）和数量估显存，超过保守阈值时预警，并提示降分辨率或改用 Canvas 渲染。
5. **真机扫码测试**：原生代码在局域网起一个静态服务器托管构建，面板出二维码；构建里注入一个诊断浮层，通过 WebSocket 把报错、FPS、内存、加载耗时回传面板。这是唯一能测到真 iOS Safari 的办法。
6. **预览设备**：贡献一组常见手机尺寸（`previewDevices`，只改视口，面板里写明不模拟 WebKit）。

**和已有功能的区别**：微信/抖音插件的 skill 只写了"对照官方文档检查包体"；web-game-studio 的 UI skill 提到安全区，但都是给 Agent 的提示，没有测量和自动修复。外部有 Lighthouse 等通用网页审计，但它不懂游戏素材（GLB、图集、音频）和各门户的预算。

**用到的能力 / 宿主缺口**
- 用到：`build: "web"`、`build.completed`、`capabilities.game`（视口变化、截图）、`capabilities.models`、原生代码（局域网服务器、gltf-transform、sharp 或按需下载工具）、`project.publish` 菜单项、`previewDevices`、面板。
- 缺口 1：`game` 会话不给网络请求明细（每个请求的字节和时间），没法精确量出"首次可交互前下载了多少"；MVP 用静态分析 + 真机浮层回传代替，希望宿主补 `session.network()`。
- 缺口 2：`build.*` 钩子只能听不能拦，发布前超预算只能提醒、不能阻止。
- 缺口 3：插件包 ≤50 MB，压缩工具链（toktx 等）要按需下载。

**怎么衡量成功**
- 用过的项目首包大小中位数的前后对比；超出所选平台预算的项目比例。
- 门户 QA 因加载、移动端问题被驳回的次数（用户回填）。
- 真机测试发现、而桌面预览没发现的问题数。

**风险与最弱点**
- **最弱点：iOS 相关问题的证据只有 bug 报告和论坛帖（E67 弱）**，也没有"iOS WebGL 崩溃导致驳回"的频率数据（证据空白）。
- 自动压缩可能伤画质，比如 Draco 精度不够、音频码率太低，所以每项都必须能看到前后对比并能撤销。
- 和 P1-05 有交界（都在发门户前用），但职责不同：本插件管"能不能快、在手机上能不能跑"，P1-05 管"SDK 和规则对不对"。两者可以共用一个"发布前检查"入口。

## P1-05 网页门户适配器（portal-adapter）

**用户与场景**：在 OhMyGame 社区发过游戏、想上有流量的西方网页门户（Poki、CrazyGames、GameDistribution、Yandex、YouTube Playables）的开发者。每家 SDK 的生命周期事件、广告调用、存档方式、驳回规则都不一样，新手往往要被驳回几轮才搞清楚。

**证据**
- E50（强）：Poki 月玩家 1 亿，2025 年有 1,018 款游戏过 1M 次游玩。E55（强）：CrazyGames 5000 万月玩家。流量真实存在。
- E9（强，GDC n>2,300）：选平台的第一驱动是受众覆盖（78%）。
- E51、E52（强，官方）：Poki 的硬规则：外部请求被拦、`gameplayStart()` 在首次输入时触发、广告只在回到游戏时调用、不许自设广告计时器、激励按钮不能是绿色且须带 🎬、广告期间静音、ESC/空格暂停、内置隐私政策链接。
- E56–E58（强）：CrazyGames 的插屏每 3 分钟最多 1 次、激励只在 adFinished 后发、Basic Launch 关广告时游戏不能留下失效按钮、≤1,500 个文件、相对路径；提交须有描述、操作说明、封面图和视频。
- E59、E62、E63、E64（强/中）：Yandex、GameDistribution、Playables、Telegram、Facebook 各有 SDK 和审核规则，且频繁变动。
- E60（中）：2025 年新作平均评分 CrazyGames 89%、Poki 81%；Yandex 评分 ≤30 持续三周即下架。E55：驳回原因包括 bug、无英文、不原创、名字是通用词。
- E66（弱，单案例）：AI 写的游戏上 CrazyGames 要补六处问题。E71（弱）：5 人工作室在 Poki 上 8 款游戏都过了 10M 次。
- E65（弱）：53% 的手游开发者计划 12 个月内把游戏移植到网页。

**做什么（MVP）**
1. **统一接口**：一个小 JS 模块，提供 `lifecycle.loading(p) / gameplayStart() / gameplayStop()`、`ads.interstitial()` / `ads.rewarded()`（回调里自动暂停、静音、锁 UI）、`storage.get/set`（落到门户的存档或带 try/catch 的 localStorage）、`user`、`openLink`。MVP 做 Poki、CrazyGames、YouTube Playables 三家，GameDistribution 和 Yandex 第二期。
2. **预览里的模拟门户**：开发模式下弹假广告层（带倒计时、可模拟"广告被屏蔽"和"广告失败"），开发者和 Agent 都能在预览里走完广告流程。
3. **规则检查**：静态部分查外部请求、绝对路径、自建广告计时器、激励按钮颜色、隐私政策链接、名字是否为通用词、是否有英文文案。运行时部分用 `capabilities.game` 触发模拟广告，读 `snapshot` 确认游戏已暂停、音频已挂起，并在广告结束后恢复。
4. **提交包**：每个门户一个导出命令（放在发布菜单），输出符合文件数和单文件上限的 zip，外加一份提交清单（描述、操作说明、封面和视频尺寸、标签），缺什么列什么；封面和视频可交给 P1-06。
5. **SDK 冲突处理**：检测到游戏用了 OhMyGame 游戏 SDK（登录、云存档、排行榜）时，在门户构建里切换到门户自己的对应能力或关闭，避免外部请求被拦导致白屏。

**和已有功能的区别**：OhMyGame 游戏 SDK 服务的是 OhMyGame 社区；wechat-minigame、douyin-minigame、taptap 插件管国内平台；西方门户和 Playables 目前**没有任何插件**。外部有各门户自己的 SDK 和文档，但没有跨门户的抽象和自动规则检查。

**用到的能力 / 宿主缺口**
- 用到：项目模板 / skill（接入统一接口）、`build: "web"` 原生命令、`project.publish` 菜单项、`capabilities.game`、面板（清单）、`files.changed`（规则即时提示）。
- 缺口 1：OhMyGame 游戏 SDK 没有"按构建目标切换后端"的机制，需要宿主允许 SDK 的存档、用户等能力由插件提供另一种实现，或者提供构建时开关。
- 缺口 2：多数门户没有公开的上传 API，MVP 只做到"生成合规的包和清单"，上传由人在门户后台完成。

**怎么衡量成功**
- 首次提交即通过门户 QA 的比例（用户回填）；从社区版到生成门户提交包的时间。
- 用插件提交到门户的游戏数；进入 CrazyGames Full Launch / Poki 正式上线的数量。

**风险与最弱点**
- **最弱点：门户收入很低**（E69：每千次游玩约 €1–$5，中位接近零），适配做得再好，多数游戏也赚不到钱。插件的价值是"拿到流量和真人数据"，宣传时不能许诺收入。
- 门户规则常变（E64 的 Facebook 就在大改），需要持续维护规则库。
- 部分门户（Poki）是邀请或审核制，开发者未必进得去。

## P1-06 商店页与短视频素材（store-kit）

**用户与场景**：游戏快做完、要开 Steam 商店页、上门户或发社交媒体的开发者。他们会做游戏，但不会剪视频、不知道 Steam capsule 有几种尺寸、商店文案写不出卖点。营销是复盘里增长最快的问题，而素材制作是营销里最可工具化的一段。

**证据**
- E9（强，GDC n>2,300）：获客渠道中社交媒体 65%、主播 39%。
- E10（强，论文）：营销是 23 年间增幅最大的复盘问题类别，"Wrong marketing strategy" 是第 3 大根因；把营销列为问题的开发者约 70% 是自发行。
- E8（弱，案例）：Next Fest 突破者靠剪辑和创作者：YAPYAP 一周 50K 条 Medal 剪辑、TikTok 约 1.5M 播放；LORT 用 jestr.gg 做了 57 个视频。
- E5（中）：表现好的游戏商店页平均上线 214 天，表现差的 411 天；首周销量约为愿望单的 0.10–0.15 倍。
- E58（强）：CrazyGames 上架须提交封面图和视频，可做封面 A/B 测试。E66（弱）：上门户时还要准备商店文案、标签、封面和玩法片段。
- E54（强）：网页玩家"more like TikTok viewers"，要在约 10 秒内展示核心能力。
- 证据空白：没有"预告片和商店页制作"耗时的定量数据，也没有"用工具做素材能提升销量"的证据。需求是强的，效果未被证明。

**做什么（MVP）**
1. **高光采集**：插件用 `capabilities.game` 跑一段脚本化或 AI 驱动的游玩并录屏（单段 ≤60 秒，可多段）；游戏可通过测试桥 `snapshot` 暴露事件（连击、击杀 Boss、过关），插件据此在时间轴上标出高光点。人工录屏（最长 5 分钟）也可导入。
2. **自动剪辑**：按高光点剪出 6 秒、15 秒、30 秒三档，16:9、9:16、1:1 三种比例，前 3 秒放最强画面并加字幕钩子，另出商店用的 GIF/WebM。用宿主的 ffmpeg。
3. **尺寸包**：一个画布预设，用游戏截图做参考图生成主视觉（图像生成由画布节点完成），再用确定性排版（sharp）输出 Steam 各 capsule、itch.io 封面、Poki/CrazyGames 封面、社区 16:10 封面，并检查标志在小尺寸下是否可读。
4. **文案**：用 `capabilities.models` 根据设计文档起草短描述、长描述、标签、操作说明，按各平台字数上限检查，中英两版。
5. **清单面板**：每个目标平台缺什么、哪些尺寸不对，一目了然；成品进 Library。

**和已有功能的区别**：内置有录屏、手动裁剪视频、社区封面；P1-07 管 Steam 的上传和节奏，素材从本插件取；P1-08 是国内买量的大批量变体。本插件只做"商店页和自然传播"这一档：数量少、质量要求高、尺寸规格多。外部有剪辑工具和 Steam capsule 模板，但它们和游戏本身、自动试玩录像不相通。

**用到的能力 / 宿主缺口**
- 用到：`capabilities.game`（recordStart/Stop、snapshot）、画布插件节点（剪辑、排版）、画布预设（主视觉流水线）、`capabilities.models`、`capabilities.library`、面板、`canvas.node` 右键命令。
- 缺口 1：插件不能直接调用图像生成模型，主视觉只能经画布节点或 Agent 生成，流程多一步。
- 缺口 2：Agent / 插件录屏单段 60 秒；长预告片要拼接多段，镜头连续性有限。

**怎么衡量成功**
- 发布到外部平台的项目中，素材"齐套"的比例；做一套素材的耗时。
- 用户回填的 CrazyGames 封面 A/B 点击率；社交平台片段播放量（手动导入）。

**风险与最弱点**
- **最弱点：工具对销量和愿望单的提升没有证据**，能证明的只有"需求存在、做这件事费时"。
- 自动选出的高光未必是人眼里的高光；AI 主视觉在 Steam 上要披露（E39），也可能招来"AI slop"印象（E40），需要和 P1-11 联动并提醒用户。
- 和 P1-08 共用"高光采集 + 剪辑"内核，下一代可以考虑合并成一个插件的两种模式。

## P1-07 Steam 上线套件（steam-launch-kit）

**用户与场景**：想把 OhMyGame 做的网页游戏（Three.js、Phaser）或 Godot 游戏卖到 Steam 的小团队。卡在三处：网页游戏怎么变成 Steam 能收的桌面包；Steamworks 的 depot、branch、steamcmd 很劝退；不知道何时开商店页、何时做 demo、何时参加 Next Fest，以及多少愿望单才算够。

**证据**
- E102（强，GDC）：最近项目 PC 占 83%；Steam Deck 28%，下一个项目 40% 对 Steam Deck 有兴趣。
- E1–E3（中）：2025 年约 2 万款新游，中位收入约 $249，40% 赚不回 $100 上架费。供给过剩的背景下，上线节奏和页面质量更要紧。
- E5（中）：首周销量约为愿望单的 0.15 倍；表现好的商店页平均上线 214 天（差的 411 天）；首 7 天好评率 91% vs 67%。
- E6（中）：节前愿望单是 Next Fest 节中增量最强的预测因子（Spearman 0.825）。E7（中）：约 7,000 愿望单进 Popular Upcoming，10 条评论后才显示评分并获得算法曝光。
- E39（中）：Valve 2026-01 新规要求披露游戏内、商店页、营销和运行时生成的 AI 内容；2025 年近 20% 的新作做了披露。
- E65（弱）：62% 的玩家在网页上发现游戏后下载或购买过，网页可以当 Steam 的漏斗。
- E97、E100（弱）：PEAK 定价不到 $5，属冲动消费，小体量游戏在 Steam 上也能起量。

**做什么（MVP）**
1. **桌面套壳**：把网页构建打包成 Windows/macOS/Linux 桌面应用（按需下载 Electron 运行时），可选接 steamworks.js 做成就、云存档和 Overlay；Godot 项目走 godot 插件已有的导出，本插件只接管上传。
2. **Steam Deck 自检**：贡献 1280×800 预览设备和手柄映射（`inputMaps`）；用 `capabilities.game` 只用手柄对应的按键跑一遍主流程，检查最小字号、是否出现只能用鼠标的界面。
3. **steamcmd 上传**：生成 app_build / depot 的 VDF，上传到指定 beta 分支；Steam Guard 验证通过 `progress` 的链接引导完成；账号密码存在插件密钥里，绝不进项目。
4. **上线节奏规划**：输入目标上线月份，生成时间线（开 Coming Soon 页、demo、Next Fest 报名窗口、主题节），附 E5–E7 的基准（愿望单分层、0.15 倍转化）和"按当前愿望单推算首周销量"的区间，并注明是估算。
5. **商店页检查 + AI 披露草稿**：截图数量、预告片、短描述长度、标签、capsule 尺寸（素材来自 P1-06）；AI 披露按 Valve 的分类生成草稿（来源数据取 P1-11，没有就扫 `.ohmygame/assets.json`）。

**和已有功能的区别**：现有插件里**没有 Steam**；引擎插件能导出，但不管 Steamworks 上传、Deck 检查和上线节奏。外部有 Steam 官方文档和 Zukowski 的营销指南，但它们和项目本身不相连。

**用到的能力 / 宿主缺口**
- 用到：原生命令（`timeoutSeconds` 最长 3600 秒，用于下载和上传）、插件设置与密钥、`progress` 链接、`previewDevices`、`inputMaps`、`capabilities.game`、`project.publish` 菜单项、面板。
- 缺口 1：Electron 运行时约百 MB，超出插件包上限，要按需下载。
- 缺口 2：愿望单和销量数据没有可靠的公开 API，MVP 用导入 Steamworks 后台导出的 CSV。
- 缺口 3：Steam 商店页本身只能在 Steamworks 网页上编辑，插件只做检查和素材准备。

**怎么衡量成功**
- 通过插件上传过构建的项目数；从"决定上 Steam"到第一个 beta 构建上传成功的时间。
- 按计划在上线前开了商店页、做了 demo 的比例；用户回填的愿望单曲线。

**风险与最弱点**
- **最弱点：没有数据说明 OhMyGame 用户里有多少人想上 Steam**。GDC 的 PC 83% 是全行业口径，OhMyGame 用户可能更偏网页和小游戏。
- 网页技术套壳的游戏在 Steam 上容易被看成"网页小品"，竞争力有限；$100 上架费和 30 天等待期也会劝退。
- 上线节奏建议基于第三方估算（中），不保证结果，要写清楚。

## P1-08 小游戏买量素材工厂（ua-creative-factory）

**用户与场景**：做微信/抖音 IAA 或混变小游戏的国内小团队。素材平均 5 天多就过期，要源源不断地出新的竖屏短视频，同时给达人提供干净的玩法素材；团队没有专职剪辑，靠人工录屏剪辑跟不上。

**证据**
- E84（中，DataEye）：2025 年小游戏投放素材超 5,012 万条（+97%）；微信素材平均生命周期 5.4 天；抖音素材总量 +153.9%，IAA 领涨。
- E85（中）：AI 素材占比已逼近真人素材；世界观剧情类素材传统约需 8 天，用 AI 约 2 天。但微信"艾米"等平台 AI 投放工具已占小游戏消耗超 1/3，所以第三方应专注**素材生产**而不是投放优化（报告结论）。
- E72（强）：小程序游戏广告变现 170.71 亿元，占 31.89%。E74（强\*）：微信 IAA 月活 4 亿，开发者八成以上是 30 人以下团队。
- E77（强\*/中）：抖音小游戏靠达人和短视频分发，达人供给 +300%。E78（中）：抖音在投 IAA 从 6,007 款增到 10,535 款（+75.4%）。
- E75（强\*）：社交渠道注册占比平均 30–50%，同样需要可分享的短片段。

**做什么（MVP）**
1. **竖屏片段采集**：用 `capabilities.game` 以 9:16 视口跑脚本化片段：差一点过关、连击爽点、失败瞬间（"99% 的人过不了这关"）。用 `setSeed` 让同一片段可以稳定复现、多次重录。
2. **变体矩阵**：前 3 秒钩子（文案模板 × 画面）× 玩法片段 × 结尾引导 × 配音/BGM（配音经画布音频节点调用 doubao-voice、fish-audio 等已有服务商）。批量渲染 20–50 条，文件名带变体编码，方便回收数据时对号。
3. **广告用语检查**：绝对化用语（"最""第一"）、诱导性承诺（"免费领""提现"）、冒用知名 IP 角色、面向未成年人的表述，逐条标出并给替换建议。注明"不构成法律意见"。
4. **数据回收与疲劳判断**：导入巨量引擎/腾讯广告后台导出的 CSV，按变体编码汇总 CTR、转化成本，按上线天数标出疲劳素材（参考 5.4 天），找出胜出的钩子并据此生成下一批。
5. **达人素材包**：无 UI 的干净片段、玩法说明、可用的梗和台词，打包给达人。

**和已有功能的区别**：微信/抖音插件只管构建和上传；P1-06 面向商店页和自然传播，数量少、规格多；本插件面向投放：数量大、迭代快、要能和投放数据对上号。外部有剪映等剪辑工具和平台自带的 AI 素材工具，它们不能直接从游戏里录出可复现的片段，也不知道游戏的事件。

**用到的能力 / 宿主缺口**
- 用到：`capabilities.game`（视口、setSeed、录屏）、画布插件节点（批量合成）、画布预设（钩子 × 片段矩阵）、宿主 ffmpeg、`capabilities.models`（文案、用语检查）、面板（数据看板）。
- 缺口 1：插件不能直接调用 TTS/图像生成，只能经画布节点，批量时依赖画布的批量运行。
- 缺口 2：小游戏运行在微信/抖音自己的运行时里，`game_use` 只能玩网页版本；如果游戏只有小游戏版本（如 Cocos 原生导出），采集要换成录 DevTools 窗口，MVP 不做。
- 缺口 3：投放平台 API 要企业账号，MVP 只做 CSV 导入，不自动上传。

**怎么衡量成功**
- 每周产出的可用素材条数和人工耗时；广告用语检查拦下的问题数。
- 用户回填的素材 CTR，以及插件生成素材与人工素材的对比。

**风险与最弱点**
- **最弱点：纯 IAA 小团队未必自己买量**（E84：IAA 只占小游戏日买量消耗的 16.6%），很多人只靠平台自然流量和社交裂变；真正大量买量的是 IAP/混变团队，而他们多有专职素材团队。
- 广告法和平台素材规范变化快，用语库要维护。
- 和 P1-06 内核重叠，见 P1-06 的最弱点。

## P1-09 风格锁（style-lock）

**用户与场景**：靠 AI 生成全部美术的程序员型开发者。主角、敌人、道具、UI 一张张生成，单看都不错，放进游戏却像三个画师画的：调色板不一样、像素尺寸不一、光源方向乱、角色和地块比例对不上。他们没有美术功底，说不清哪里不对，只觉得"看起来很 AI"。

**证据**
- E15（弱，n=122）/ E31（强，论文）：46.7% 的学员预计要外包美术、音频；人手和技能不足是复盘第一根因（49 次）。
- E45（弱，厂商 / 强，论文）：AI 像素画不对齐网格、像素尺寸混杂、上百种近似色；跨帧保持风格、比例、细节一致需要大量手工。
- E42（弱）：Godogen 的 2D sprite "a bit of a mess"。
- E32（中）：国内企业美术环节 AI 渗透率 84.2%，生成美术已是普遍做法。
- E33（强，GDC）：视觉美术 64% 对 GenAI 持负面看法。定位只能是"让非美术的人做出一致的东西"，不能是"替代美术"。
- E39（中）：Steam AI 披露中约 60% 是视觉素材（未核实）。
- 证据空白：**美术风格一致性没有定量数据**（EVIDENCE 文末明确列出），这条证据偏弱。

**做什么（MVP）**
1. **风格圣经**（面板编辑，存为 `design/style.json` 并附锚点图）：调色板（手填或从定稿图里提取）、像素密度或线宽、描边颜色、光源方向、镜头角度、各类素材的标准尺寸（角色、地块、图标）、负面词。
2. **生成前注入**：`image.beforeGenerate` 钩子把风格圣经压缩成一句约束追加到提示词，按素材类型改尺寸，精灵强制透明背景。Library 会记下插件改了哪些字段（宿主已支持）。
3. **入库自动审查**：`asset.added` 触发。像素风格：对照**项目调色板**算出界颜色比例，像素尺寸是否与项目一致，脚底和锚点是否与同类素材对齐（单张指标的算法与内置 Check pixel art 一致，本插件补的是"对照项目标准"）。非像素风格：色温、饱和度直方图与锚点图的距离；再用多模态模型做"这张和锚点图像不像同一个游戏"的打分。结果以 toast 提示，并写进面板。
4. **风格漂移看板**：全部素材按漂移分数排成接触表，可一键"量化到项目调色板"（画布插件节点），或"带锚点图重新生成"（填进 Composer 或画布）。
5. **3D 预算**：glTF 的面数、贴图尺寸、材质数，以及缩放、轴向、轴心统一（gltf-transform），超出预算时提醒。

**和已有功能的区别**：内置的 Fix / Check pixel art 是对选中图片手动执行的单张工具；sprite-pipeline skill 是给 Agent 的做法说明；pixellab、aseprite 负责生成和编辑。本插件补的是**项目级标准**和**自动执行**：每次生成前约束、每次入库后对照全项目检查。pixelfx 管特效和音效，不重叠。

**用到的能力 / 宿主缺口**
- 用到：`image.beforeGenerate`、`asset.added`、面板（Library 接触表）、画布插件节点、`capabilities.models`（图片输入）、原生代码（sharp、gltf-transform）。
- 缺口 1（关键）：`image.beforeGenerate` **不能添加参考图**，而参考图恰恰是保持一致最有效的手段。希望宿主允许钩子追加 `references`（限项目内文件）。
- 缺口 2：内置 Check pixel art 的算法没有开放给插件，插件要么自己重写（会产生两套口径），要么等宿主开放 `check-pixel-art` 接口。

**怎么衡量成功**
- 新素材首次生成即通过审查的比例；每个被采纳素材平均重新生成的次数。
- 风格圣经设定后，漂移分数的项目内方差变化。
- 用户手动标记"风格不一致"的次数。

**风险与最弱点**
- **最弱点：没有定量证据说明"风格不一致"有多常见、多严重**，只有厂商内容和轶事。
- 提示词注入对一致性的提升有限，真正有效的是参考图，这依赖宿主补缺口 1。
- "像不像同一个游戏"的模型打分主观且不稳定，只能当提示，不能当门禁。

## P1-10 拼装骨骼动画（cutout-rig）

**用户与场景**：已经有一张满意的主角立绘或精灵，需要它走、跑、跳、攻击、受击的开发者。用 AI 生成动作帧表，每帧长得都不太一样（脸变了、衣服变了、比例漂了）；手绘帧动画又不会。动画是 AI 做游戏最大的缺口之一。

**证据**
- E42（弱）：Godogen 作者自认**动画是主要缺口**，demo "felt really lifeless"。
- E45（弱/强）：AI 动画帧会"blur, warp, or slide across the grid"，动作"smoothed instead of keyed"；静态 sprite 尚可，连贯的动画帧很难（Sprite Sheet Diffusion 论文）。
- E32（中）：国内企业 AI 在动态内容（动作捕捉、UI 动效）的渗透率只有 31.3%，静态美术是 84.2%，差距明显。
- E28（强，论文）：问答站上 animation 问题 60% 没有采纳答案，rigging 76%，blending 70%，属最难得到帮助的一类。E27（强）：animation 有 685 个问题。
- E44（弱）：手感和打磨（含动画反馈）没法一次生成。

**做什么（MVP）**
1. **部件准备**：三种入口：(a) 画布预设，让图像模型在**同一张图**里画出拆开的部件（头、躯干、上下臂、腿），再用内置网格切分；(b) 导入 Aseprite/PSD 分层文件；(c) 对单张立绘用多模态模型给出部件框选建议，人在面板里微调。
2. **绑骨面板**：自动建议关节轴心，可拖动调整；只做刚性部件，不做网格变形，以降低难度。
3. **程序化动作库**：待机呼吸、走、跑、跳（挤压拉伸）、攻击（预备 → 出手 → 收招）、受击、死亡。每个动作的节奏、幅度、夸张度都是参数，可写进 `tuning.json`，在调参面板里实时调。
4. **导出**：轻量 JSON + 一个很小的运行时（Phaser、Three/R3F、PixiJS），Godot 生成 AnimationPlayer 场景；也可"烘焙成帧表"给任何引擎和小游戏用。像素风格烘焙时用最近邻采样并限制旋转角度，减少锯齿。
5. **游戏内预览**：按游戏实际尺寸预览，可用 `capabilities.game` 截取动作序列供 P1-01 或人检查。

**和已有功能的区别**：内置的 Continuous actions (V4Tx3) 让图像模型直接画动作帧，一致性取决于模型；本插件从**一张定稿图**出发，一致性由构造本身保证。Aseprite 插件是逐帧手绘工具。外部有 Spine（付费、学习成本高）、DragonBones（已基本停更），都不在 OhMyGame 的流程里，也不接 Agent。

**用到的能力 / 宿主缺口**
- 用到：面板（绑骨编辑器）、画布预设和插件节点（部件拆分、烘焙）、`capabilities.models`（部件建议）、`capabilities.library`、项目模板/skill（运行时接入）、`capabilities.game`（预览截取）。
- 缺口：无硬缺口。部件拆分的质量依赖图像模型能否在一张图里画出干净的分件，这一点要实测。

**怎么衡量成功**
- 用插件产出并进游戏的角色动画数；从定稿角色到能走能跳的耗时。
- 同一角色各动作的一致性（对照锚点图的相似度）与 V4Tx3 帧表的对比。
- 被用户删掉、改回帧动画的比例。

**风险与最弱点**
- **最弱点：拼装动画有明显的"纸片人"观感**，不适合所有风格；精细像素画旋转后会走样。
- "开发者需要拼装骨骼动画"的需求证据是间接的：证据只说明动画难、AI 帧不一致，没有说明拼装方案会被接受。
- 编辑器类面板开发量较大，MVP 要严格只做刚性部件。

## P1-11 素材来源与 AI 披露账本（provenance-ledger）

**用户与场景**：要把游戏发到 Steam、CrazyGames、Reddit 黑客松或国内平台的开发者。上架时要回答"哪些内容是 AI 生成的""这个模型和音效从哪来、能否商用"。项目里的素材有的是生成的，有的来自 Sketchfab（CC-BY 要署名、CC-NC 不能商用），有的是 Agent 从网上找的，几个月后谁也说不清。

**证据**
- E39（中）：2025 年近 20% 的 Steam 新作披露了 GenAI；Valve 2026-01 新规要求披露游戏内、商店页、营销中的 AI 内容，以及运行时生成的内容，代码助手不用披露。
- E40（中/弱）：GameDiscoverCo 调查（约 3,800 人）中 8% 的玩家表示绝不购买；玩家普遍怀疑开发者隐瞒 AI 使用。
- E36（弱，厂商）：63% 担心数据所有权，32% 担心 AI 产出归属不清。
- E48（中/弱）：Unity AI 把版权责任转给用户。
- E55（强）：CrazyGames 驳回不原创（克隆、素材换皮）的游戏。E63（强）：Reddit 黑客松禁止 "obvious AI slop"。E47（弱）：Astrocade 被评价"copyright infringement"。
- E34（强）：51% 的公司有 AI 政策（AAA 78%）。

**做什么（MVP）**
1. **自动记账**：以 `.ohmygame/assets.json`（宿主已记录提示词、来源、Library 链接）为底，用 `asset.added`、`image.beforeGenerate`（记下实际用的模型）、`tool.afterCall`（Agent 的下载和生成工具）、`files.changed`（发现来路不明的新文件）补全，形成 `provenance.json`：文件哈希、来源类型（生成 / Library 来源 / 外部下载 / 手作）、模型或作者、授权、原始链接、日期，以及是否经过人工修改。
2. **授权检查**：CC-BY 需署名、CC-NC 与商业目标冲突、未知授权、Sketchfab 和 Openverse 等来源授权映射；与项目的目标平台（商业 / 非商业）对照。
3. **构建映射**：`build: "web"` 时列出真正进包的文件，标出其中没有来源记录的那些。
4. **导出**：Steam AI 披露草稿（区分预生成和运行时生成）、游戏内署名页（CREDITS）、门户和 itch.io 的说明文字。
5. **发布前提醒**：发布菜单里的"来源检查"；`build.started` 时如有进包的未知来源文件，弹 `danger` toast。

**和已有功能的区别**：宿主只记录单个素材的提示词和来源，没有授权汇总、进包映射和披露导出；Sketchfab 插件只负责搜和下载。外部没有面向 AI 游戏项目的同类工具。

**用到的能力 / 宿主缺口**
- 用到：hooks（`asset.added`、`image.beforeGenerate`、`tool.afterCall`、`files.changed`、`build.started`）、`build: "web"`、面板、`project.publish` 菜单项、`capabilities.models`（起草披露文字）。
- 缺口 1：`build.started` 只能听，不能拦下发布。
- 缺口 2：Library 来源插件返回的 `license` 字段是可选的，来源插件不填，账本就是空的；需要宿主或来源插件规范授权字段。
- 缺口 3：原生编码 Agent（Claude Code、Codex）自己用 curl 下载的文件，工具钩子看不到，只能靠 `files.changed` 事后发现，来源记为"未知"。

**怎么衡量成功**
- 进包文件中有来源记录的比例；发布前被拦下的授权问题数。
- 生成 Steam 披露、署名页的项目数。

**风险与最弱点**
- **最弱点：开发者"痛"的频率证据偏弱**，E36 是厂商调查；强证据（E39、E55、E63）是平台规则，说明"必须做"，但没说明"开发者为此很痛苦"。
- 很多用户只发 OhMyGame 社区，用不到披露。插件的价值集中在要上 Steam 和门户的那部分人，适合作为 P1-07 / P1-05 的前置模块，而不是独立卖点。下一代可以考虑合并。

## P1-12 代码护栏与引擎版本参考（code-guardrails）

**用户与场景**：项目做了几周、功能越来越多的创作者。每加一个功能 Agent 就弄坏另一个，或者把一个文件整个重写；Godot 项目里 Agent 写出 Godot 3 的 API（`KinematicBody2D`、`yield`），Three.js 项目里用了早已移除的 `THREE.Geometry`。项目越大越不敢动。

**证据**
- E43（弱，多篇博客）：随着游戏模式增加，代码"quickly became … unacceptable"；加一个组件常破坏另一个；像重写而不是修改。缓解办法：在 CLAUDE.md 写死模式、目录结构、依赖的硬规则后，一致性明显提升。
- E42（弱）：Claude 混淆 Godot 3 和 4 的 API，Godogen 作者为此自建 GDScript 参考和"quirks database"，由 Agent 按需加载。
- E37（弱，厂商 n=651）：模型质量和准确性是 AI 落地的第一障碍（53%）。
- E108（强/中）：GMTK jam 中 Godot 份额从 16%（2022）升到 47%（2026）；新独立工作室 11% 用 Godot。Godot 新人多，版本混淆的受害面在变大。
- E38（弱）：50% 用 MCP 服务器，其中 90% 用来连接引擎和编辑器。
- E12（强）：technical 问题占复盘 11%，是最大的一类。

**做什么（MVP）**
1. **架构规则文件** `design/architecture.md` + 机器可读的 `guardrails.json`：模块边界（谁能 import 谁）、锁定的核心文件、单文件行数上限、禁止新增依赖或须审批。通过 `contributes.instructions` 让每个 Agent 都读到。
2. **工具调用前拦截**：`tool.beforeCall` 对 Pi Agent 和 OhMyGame 工具的写文件调用做检查：写入锁定文件或整文件重写超过 N 行时返回 `ask`；命中已知错误 API（按项目的引擎和版本）时返回 `deny`，并在 reason 里给出正确写法，让 Agent 当场改。
3. **事后审查**：原生编码 Agent 绕过工具钩子，所以 `turn.completed` 和 `files.changed` 再扫一遍本轮改动（错误 API、越界 import、重复代码），有问题弹 toast，提示撤销或修复。
4. **腐化趋势**：每轮记录文件数、最大文件行数、循环依赖、重复率、TODO 数，面板画趋势；越过阈值时建议"先重构再加功能"，并给出建议的拆分方案（发给 Agent）。
5. **版本锁定参考包**（skills）：Godot 4.x 怪癖库（含 3 → 4 改名对照）、Phaser 3/4、Three.js 近期破坏性变更、Cocos 3.8；按项目实际版本加载。

**和已有功能的区别**：检查点、撤销和 Git 只能事后回滚；claude-code-game-studios 模板提供 CLAUDE.md 规则，只对 Claude Code 生效，而且是"写了规则"而不是"执行规则"；引擎插件负责连接编辑器，不检查 API 版本。

**用到的能力 / 宿主缺口**
- 用到：`tool.beforeCall`（ask/deny，带"允许并记住"）、`turn.completed`、`files.changed`、instructions、skills、面板、原生代码（AST 分析）。
- **缺口（关键）**：文档写明"Native coding agents' own file/shell tools … are outside this boundary"。用户选 Claude Code 或 Codex 时，`tool.beforeCall` 拦不到它们的文件编辑，只能事后发现。可选做法：(a) 宿主把原生 Agent 的文件编辑也转发到钩子；(b) 插件经用户同意，在项目里写入 Claude Code 自己的 hooks 配置（侵入性强，作为可选项）。

**怎么衡量成功**
- 被拦下或事后发现的错误 API 次数；同类错误的复发率。
- 加入护栏后，"回退上一个检查点"的频率；腐化指标曲线的斜率。
- 用户对"Agent 改坏别的功能"的抱怨或返工回合数。

**风险与最弱点**
- **最弱点：证据全是轶事和厂商调查**（E43、E42、E37），只有 Godot 增长（E108）是较强的数据，而它只说明受众在变大，没有直接证明"版本混淆"的频率。
- 规则太严会频繁打断 Agent，太松又没用；默认规则集要保守。
- 参考包随引擎版本更新，需要维护。

## P1-13 小游戏提审与资质预检（minigame-compliance）

**用户与场景**：第一次发微信或抖音小游戏的个人开发者或小团队。网上说法互相矛盾：纯 IAA 要不要版号？软著怎么写？自查报告是什么？提审被驳回，原因是录屏异常、登录失败，或者包里残留了没用的支付 SDK。

**证据**
- E74（强\*）：微信小游戏开发者超 50 万，八成以上是 30 人以下团队。E75（强\*）：2025 年约 5000 名开发者首次发布游戏。首次发布的人最容易卡在资质上。
- E81（弱/中）：说法混乱。普遍说法是纯 IAA 可免版号，但需软著 + ICP 备案 + 自查报告；律所认为原则上都要版号，无版号运营有处罚风险；ICP 约 7–20 个工作日，版号 4–8 个月、数万到十几万元。
- E83（强，官方 / 弱）：TikTok 验收指南列出的驳回情形有录屏功能异常、登录失败、支付异常、抽奖/现金类活动违规；Cocos 论坛案例中，残留的第三方支付 SDK 导致被拒。
- E90（弱）：国内独立开发者缺钱、版号难，约一半团队只有一人。
- E82（强）：主包 4 MB / 总计 30 MB（包体部分交给 P1-04）。
- 判断：受影响人数有平台口径的数据（E74、E75），痛点本身的证据弱，且法规口径本身就不统一。

**做什么（MVP）**
1. **资质判断树**：按变现方式（IAA / IAP / 混变）、是否强联网、主体（个人 / 企业）、目标平台，列出需要的材料（软著、ICP 备案、自查报告、版号、实名和防沉迷），每条附来源链接和核对日期，醒目标注"不构成法律意见，以平台和主管部门最新要求为准"。
2. **软著材料草稿**：从项目源码中按常见格式抽取、排版程序鉴别材料（去除注释中的密钥、第三方库），并用 `capabilities.game` 自动截图生成操作说明书初稿。
3. **自查报告、隐私政策、用户协议**的模板草稿，按游戏实际收集的数据（扫描代码里的存储、网络和登录调用）填写。
4. **提审前扫描**：残留的支付、广告、统计 SDK；隐私接口调用与声明不一致；适龄提示和健康游戏忠告是否存在；IAP 游戏是否接了防沉迷。
5. **验收自测清单**：按抖音验收指南和微信常见驳回原因列出，能自动检查的（静态扫描）自动打勾，需要真机的（录屏、登录、支付）给出具体步骤。

**和已有功能的区别**：wechat-minigame、douyin-minigame 插件只管构建、预览和上传，明确把"审核"留给人；没有任何插件处理资质和材料。外部有付费代办服务，不接项目代码。

**用到的能力 / 宿主缺口**
- 用到：skills（判断树和模板）、原生命令（源码抽取、排版成 docx/pdf）、`capabilities.game`（网页版截图）、`capabilities.models`（起草）、面板（清单）、`project.publish` 菜单项。
- 缺口 1：小游戏跑在微信/抖音自己的运行时，`game_use` 碰不到，录屏、登录、支付这类检查无法自动化（wechat-minigame skill 也说明 DevTools 的自动化看不到游戏画布）。
- 缺口 2：法规和平台规则变化快，模板需要有人持续维护并标注日期。

**怎么衡量成功**
- 首次提审通过率（用户回填）；准备材料的耗时。
- 扫描拦下的残留 SDK、隐私声明不一致问题数。

**风险与最弱点**
- **最弱点：证据弱，且有法律风险**。E81 自身就互相矛盾，插件给出的结论一旦出错，代价由用户承担。只能定位为"整理材料 + 提示风险"，不能给结论。
- 软著、ICP 本身需要人去提交和等待，插件省的是准备时间，等待时间省不了。

## P1-14 必发计划（ship-plan）

**用户与场景**：所有在 OhMyGame 里开新项目的人，尤其是参加 Jam、第一次做游戏、或已经做了三个月仍没发出去的人。开头热情高、范围一路变大，Agent 让"再加一个功能"变得太容易，最后项目停在 80%。

**证据**
- E12（强，论文，927 个问题）：planning + scope + feature creep + cutting features + delays 合计约 20%。
- E13（强）：根因里 Underestimation 34 次、Unclear game design vision 28 次；作者建议多做预制作和原型。
- E14（强，论文）：出错的前几位里 schedule 25%、development process 24%；小团队 50% 列出 obstacles；引语 "Feature creep ruled our roost"。
- E16（中，计算）：大型 jam 只有约 10–30% 的报名者提交作品。E17（中）：Ludum Dare 约一半草稿没有发布。E89（中）：聚光灯 GameJam 完赛率约 50–60%。
- E18（弱）：没做完的原因是时间、范围，以及"导出后才发现要大改"，于是交晚了。
- E15（弱，n=122）：缺纪律、缺时间最高，缺规划"高于预期"。
- E97（弱，单案例）：PEAK "We avoided scope creep by having a built-in ship date"。
- E19（中/弱）：仅 25% 的 Early Access 游戏正式发布。
- 判断：这是频率证据最硬的痛点之一；"工具能否改善完成率"没有证据。

**做什么（MVP）**
1. **开局三问 → 一页设计意图卡**：发布日期、目标平台、一句话核心玩法，由插件扩展成意图卡（支柱、核心动词、10 秒钩子、单局时长、参考游戏、**明确不做的清单**），写进设计文档，并通过 instructions 让 Agent 每次动手前对照。
2. **里程碑阶梯**，每级都有可机检的完成条件：可启动 → 核心循环可玩 → 有失败、胜利和重开 → 有标题和结束画面 → 可分享（发到社区，哪怕很丑）→ 可上架（如装了 P1-04、P1-05，就接入它们的检查结果）。能用 `capabilities.game` 自动验证的就自动打勾。
3. **范围漂移监测**：`turn.completed` 用 `capabilities.models` 把本轮的请求和改动分类为"计划内 / 打磨 / 新功能"。新功能超出预算时弹 toast，把它放进"以后再说"清单，并给出削减建议。
4. **时间预算**：按历史回合推算每级里程碑的耗时，和发布日对比，出"按当前速度会晚 X 天"的提示，并列出可砍项。
5. **Jam 模式**：倒计时；截止前 24 小时自动提醒先出一个能提交的构建（针对 E18 的"导出太晚"）；可一键发布到社区作为保底。

**和已有功能的区别**：game-studio skill 在开局时定"首个可玩范围"，之后不再跟踪；内置的 Agent 通知只报"完成了"，不报"偏了"。外部有 Trello、HacknPlan 等项目管理工具，它们看不到项目本身的状态，也不能自动验收。

**用到的能力 / 宿主缺口**
- 用到：`turn.completed`、`capabilities.models`、`capabilities.game`、instructions、面板、项目模板（新建项目时的问卷）、`home.starters`（Jam 模式入口）、`project.toolbar`。
- 缺口 1：没有"用户消息到达、Agent 开始前"的钩子，没法在加新功能**之前**提醒，只能事后提醒或靠 instructions 让 Agent 自觉。
- 缺口 2：插件之间不能互相调用（plugin-plan 明确不做跨插件调用），接入 P1-04、P1-05 的结果只能通过读它们写在项目里的报告文件。

**怎么衡量成功**
- 项目从创建到第一次发布到社区的天数中位数；创建后 30 天内有过发布的项目比例。
- Jam 模式用户的完成率，对比公开基准（LD 约 50%，E17）。
- 被放进"以后再说"清单、最后真的没做的功能比例（说明砍得对）。

**风险与最弱点**
- **最弱点：工具能否提升完成率没有任何证据**；"缺动机、缺时间"（E15）不是工具能解决的。
- 提醒过多会让人反感，需要能调低频率或关闭。
- 和 game-studio 的设计流程有交界，要避免两份设计文档。

## P1-15 联机网络实验室（netcode-lab）

**用户与场景**：用 OhMyGame 多人 SDK 做实时联机（合作物理喜剧、派对游戏、.io 类）的开发者。本地测试一切顺滑，发出去后玩家互相瞬移、打中了却不算；想和朋友用手机在同一个局域网里测，连不上本地服务；想把游戏做成 Discord Activity，又被 iframe 代理和 CSP 卡住。

**证据**
- E28（强，论文）：multiplayer 问题 56% 没有采纳答案，collider 63%。联机属于最难得到帮助的一类。
- E30（弱，厂商 n=300）：83% 支持在线多人，55% 主打 2–9 人；38% 认为跨设备一致的体验是主要障碍。
- E49（中）：Vibe Jam 2026 偏好多人游戏；945 款作品中约 5% 用 Colyseus。
- E97–E100（弱/中）：2025 年三款小团队爆款（R.E.P.O.、PEAK、Schedule I）合计 4200 万份以上，好友合作是主要方向之一。
- E63（强，文档）：Discord Activities 跑在沙盒 iframe 里，走 Discord 代理和 CSP，外部域名要配 URL Mappings，本地隧道开发和生产表现不同；要给中途加入的玩家安排事做。
- OhMyGame 自己的文档（multiplayer.md）：本地测试"run on loopback with almost no latency, so they do not show how prediction and smoothing look over a real network"；本地后端只监听回环地址，别的设备连不上。这是宿主自己写明的空白。

**做什么（MVP）**
1. **网络条件模拟**：给每个测试玩家设延迟、抖动、丢包（预设：同城 Wi-Fi、4G、跨洲）。插件在原生代码里起一个可配延迟的 WebSocket 中继，夹在游戏和本地多人服务之间，用 SDK 已有的"固定本地 URL"方式接入。宿主的 SOCKS 代理如能开放延迟参数会更干净（见缺口）。
2. **多端分叉检测**：用 `game.actTogether` + `samples` 在延迟条件下同时操作 2–4 个玩家，对比各端 `snapshot` 中的关键字段（位置、血量、分数），画出分叉时间线，超过阈值时截下各端画面并排展示。
3. **平滑效果对比录像**：同一段操作分别在 0 ms 和 150 ms 下录屏，并排播放，让人直观看到插值、预测参数（SDK 的 `delayMs`、`maxExtrapolateMs`）的效果，参数可调。
4. **局域网多真机**：原生代码把本地多人服务和游戏构建转发到局域网，面板出二维码，朋友的手机扫码即可加入同一个房间。
5. **Discord Activity 导出**：生成 Embedded App SDK 接入代码和 URL Mappings 配置，检查外部请求是否都走了映射，提供隧道式的本地测试；把 SDK 的房间映射到 Discord 的 instance。

**和已有功能的区别**：SDK 已有预测、插值、drop-in 房间、观战、`simulateRoom`；`game_use` 和插件能 2–4 人同时操作、断网和刷新；Game Tests 做脚本化的多人回归测试。本插件只补宿主文档里写明的空白：**非零延迟**、**多真机**、**Discord 渠道**，以及延迟下的分叉检测。

**用到的能力 / 宿主缺口**
- 用到：`capabilities.game`（`actTogether`、`samples`、`networkControl`、录屏）、原生代码（中继、局域网转发）、面板、skill（Discord 接入）、`project.publish` 菜单项（Discord 导出）。
- 缺口 1：`setOnline` 只有开和关，希望宿主在已有的 SOCKS5 代理上加 `setNetworkConditions({ latencyMs, jitterMs, lossPct })`，这样不用插件自己做中继，也能覆盖 P2P 直连。
- 缺口 2：插件录屏和 `actTogether` 的并发上限是 4 人。
- 缺口 3：Discord Activity 上线需要开发者自己的 Discord 应用和公网可达的多人服务，OhMyGame 的游戏服务是否能被 Discord 代理映射，需要和宿主确认。

**怎么衡量成功**
- 在延迟模拟下发现、在 0 延迟下没发现的问题数。
- 用局域网多真机测过的联机项目比例；导出为 Discord Activity 的游戏数。
- 联机游戏发布后，玩家评论中"卡、瞬移、不同步"的提及率（结合 P1-03 的聚类）。

**风险与最弱点**
- **最弱点：频率证据主要是厂商数据**（E30 弱），较强的 E28 只说明联机难，没说明 OhMyGame 用户有多少在做实时联机。
- 和 Game Tests（多人回归）以及宿主多人功能的边界要事先和维护者对齐，否则容易被判为重复。
- Discord Activity 的分成和政策仍在变（E63 中 GamesBeat 的费率未确认）。

### 没有覆盖的痛点与原因

- **音频（痛点 9 的一半）**：EVIDENCE 文末明确列出"没有 AI 音频、音效、音乐、配音失败模式的证据"，已有 elevenlabs、fish-audio、minimax 等服务商插件，pixelfx 正在做像素音效。没有证据就不硬凑，下一代如证据库补上再提。
- **着色器**（E27 中 980 个问题，E28 未列为最难）：有提问量，但和 OhMyGame 的流程结合点不清楚，Agent 已能写着色器，缺的是验证，这一点由 P1-01 的视觉评审部分覆盖。暂不单列。
- **iOS 原生导出 / Xcode**（E29 最难解决）：OhMyGame 以网页和小游戏为主，原生 iOS 导出属于引擎插件的范围，用户面窄。
- **本地化**（E104，未进高频索引）：只有厂商的 45% 一条比例，"哪些语言回报高"没有数据；PEAK 和 Poki 的建议是"少用文字"，这更像设计约束，可写进 P1-14 意图卡和 P1-04 规则，而不是单独的插件。
- **资金、裁员、crunch、版号周期、平台流量分配、供给过剩**（E3、E90、E105–E107、E81）：工具解决不了，不提插件。
- **买量投放优化**：平台自带的 AI 投放工具已占大头（E85），第三方插件没有优势，P1-08 只做素材生产。
- **Telegram、Facebook Instant、Reddit Devvit 适配**：规则变动大（E64），OhMyGame 用户需求未知，留作 P1-05 第二期的候选。

## 生成者自评：候选间的重叠与下一代可合并项

- **P1-06 与 P1-08** 共用"高光采集 + 自动剪辑"内核，区别在用户（Steam/门户 vs 国内投放）和规模。若评审认为差异不够，建议合并为一个"营销素材"插件的两种模式。
- **P1-04 与 P1-05** 都在"发布前"使用，可共用一个"发布前检查"入口，但职责可分（性能和设备 vs SDK 和规则）。
- **P1-11** 单独做的需求偏弱，更像 P1-07（Steam 披露）和 P1-05（原创性）的前置模块，可合并进其一。
- **P1-01 与 Game Tests**（进行中）在"多人、回归"上有交界，本提案刻意只做独立评审、不变式和回合级提示；需要维护者确认边界。
- **P1-15** 的网络模拟最好由宿主直接补（在已有 SOCKS5 代理上加延迟参数），插件只做分叉检测、真机和 Discord。如果宿主愿意补，这个候选会变小。
- 证据最强的五个（按数据强度粗排，仅供评审参考）：P1-04（多条官方规则 + Cannon Clash 数据）、P1-05（官方规则 + GDC 78%）、P1-14（两篇论文 + jam 漏斗）、P1-06（GDC 65%/39% + 论文）、P1-07（GDC PC 83%）。证据最弱的：P1-01、P1-12、P1-13（轶事、厂商调查或口径混乱），其中 P1-01 和 OhMyGame 的契合度最高，值得在下一代补证据而不是直接淘汰。
