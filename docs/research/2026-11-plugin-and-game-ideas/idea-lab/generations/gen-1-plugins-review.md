- 依据：`GOAL.md`、`RUBRIC.md`、`CONTEXT.md`、`EVIDENCE.md`（E1–E110）、`generations/gen-1-plugins-proposals.md`。
- 核对过的代码和文档：`ohmygame`（dev，d6eac678，beta.5.11）的 `docs/plugins.md`、`runtime.md`、`preview-runtime.md`、`media-tools.md`、`canvas-agent.md`、`multiplayer.md`、`plugin-plan.zh-CN.md`，`src/daemon/agent-prompts.ts`、`src/daemon/canvas-routes.ts`、`src/shared/contracts.ts`、`packages/game-sdk/src/`；`ohmygame-plugins/plugins/` 下 36 个插件；`origin/feat/game-tests`（768b9c5，标签 game-tests-v0.1.0）的 README。
- 评分：每项 1–5 分。权重：频率 ×5、严重度 ×4、证据 ×4、契合 ×3、可行 ×2、差异 ×2，满分 100。没有证据支撑的维度最多给 2 分。

## 0. 先说结论

1. **没有一个候选能原样进终选。** 分数最高的 P1-14（82）、P1-04（81）、P1-03（73）方向都对，但要么效果没证据，要么依赖宿主补缺口，要么和宿主已有功能部分重叠。
2. **生成者漏查了几处重要的已有能力。** 代码核对发现：
   - **PixelLab 插件已经能做骨骼动画、从一张图生成帧动画、补中间帧、出 8 个朝向**（`pixellab/README.md` 第 45–51 行）。P1-10 没提到它。
   - **claude-code-game-studios 模板已带按版本锁定的引擎参考**（`docs/engine-reference/{godot,unity,unreal,web}/deprecated-apis.md`、`breaking-changes.md`），以及 `scope-check`、`cut`、`sprint-plan`、`milestone-review`、`balance-check`、`art-bible`、`launch-checklist`、`localize` 等 78 个 skill 和 `validate-write.sh` 等 hooks。它和 P1-12、P1-14 部分重叠，和 P1-02、P1-09 小部分重叠。但这些只对用这个模板、用 Claude Code 开的项目生效。
   - **内置 Check pixel art 不是只看单张图。** 选多张图时，它会报告这些图的尺寸和脚底行是否一致、合计用了几种颜色，并按像素密度（8/16/48 色）检查调色板预算（`media-tools.md` 第 124–147 行）。P1-09 说它是"单张工具"，不准确。
   - **发布对话框已经显示包体**：总大小、文件数、最大的文件和顶层文件夹，对照 100 MiB 上限；发布时还会无损重压 PNG（`runtime.md` 第 1238–1265 行）。P1-04 的"包体报告"和它部分重叠。
   - **预览已内置 mobile、tablet、mobile-landscape 三种设备**（`src/shared/contracts.ts:18`），所以 P1-04 第 6 项"贡献手机尺寸"几乎没有增量。
   - **宿主的 ffmpeg 没有开放给插件。** 宿主带了 `ffmpeg-static`，但只给自己的媒体工具用，`plugins.md` 没有任何插件接口（`media-tools.md` 第 77–85 行）。P1-04、P1-06、P1-08 写的"复用宿主的 ffmpeg"是未写进文档的依赖。
   - **Game Tests 的范围比提案说的大**：每一步都能检查 `snapshot()` 状态、画面、控制台报错和失败请求；它的 instructions 要求 Agent 改完有测试的游戏后自己跑测试。宿主系统提示词也要求 Agent 在回合末尾说明哪些行为没验证（`agent-prompts.ts:19`）。P1-01 和它们的重叠比提案承认的多。
3. **契合度有一个共同的盲点：不知道 OhMyGame 用户实际发到哪里。** EVIDENCE 文末写明"没有 AI 原生做游戏产品的留存或使用量数据"。仓库特征（中文文档、+0800 时区、微信、抖音、TapTap 插件）说明国内用户占比可能不小，但 P1-05 只做西方门户，国内小游戏的 **IAA 广告和分享接入**反而没有候选（见第 3 节）。
4. **建议合并**：P1-06 和 P1-08 合并；P1-04、P1-05、P1-11 合并，再加上 P1-13 的残留 SDK 扫描（宿主不支持跨插件调用，见 `plugin-plan.zh-CN.md` 第 42 行，分开做只能靠读写彼此的报告文件）。P1-12 不再单独做。

## 1. 逐个评审

### P1-01 试玩验收官（proof-of-play）

**证据核对**
- E41、E42、E44 都是轶事，但来源互相独立（HN 上两个帖子、Decrypt、Godogen），方向一致：Agent 会误报"运行完美"，只看截图的独立评审能抓到画面 bug。
- E36 的 47% 是"用 AI 做试玩与平衡"的**采用率**，不是"Agent 误报"的发生率。拿它证明痛点频率属于**过度引用**。
- E23（testing 5%）是职业团队复盘的数据，和 AI agent 误报无关，只能当背景。
- 结论：需求证据实际上**只有轶事**，没有比例数据，碰到 RUBRIC 的致命项"需求证据只有轶事"。

**致命问题检查**
- **只有轶事**：成立，有致命风险。唯一的出路是拿 OhMyGame 自己的数据：在示例游戏里埋入已知 bug，统计 Agent 说"完成"但游戏实际坏了的回合占多少。这个数据下一代必须补上。
- **重复**：部分成立。
  - Game Tests 负责脚本化断言（snapshot、画面、控制台、失败请求），并要求 Agent 改完代码后自己跑。
  - web-game-studio 的 game-playtest 和 game-studio 的 game-qa 已写明"检查独立不变式"，并提醒"截图空白检测只是预警"。
  - 宿主提示词要求 Agent 报告哪些行为没验证。
  - 真正新的只有两点：**和写代码的 Agent 隔离、只看画面的评审**，以及**用钩子客观判断本轮有没有运行证据**（不靠 Agent 自己说）。
  - "逐帧不变式"本质上是 Game Tests 断言的连续版，应作为 Game Tests 的功能提出，不该另做一个插件。
- **可行**：可以做。
  - `turn.completed` 只能弹 toast，不能把问题退回给 Agent（已核实 `plugins.md` 第 532 行起）。
  - 模型调用每插件 3 并发、每分钟 30 次（已核实）。
  - 插件会话能不能调用测试桥的 `step`，文档没写明，要实测。
- **契合**：最高。这正是 OhMyGame 的核心承诺。

**评分**

| 维度 | 分 | 理由 |
|---|---|---|
| 频率 | 3 | E41、E42、E44 多个独立轶事，方向一致，但没有比例数据 |
| 严重度 | 3 | 造成返工和信任损失（E43），没有证据说明会导致项目放弃 |
| 证据 | 2 | 全是弱证据；E36 引用过度 |
| 契合 | 5 | 落在 Agent 写代码加试玩的核心回路上 |
| 可行 | 4 | 扩展点都在；缺"回合结束退回 Agent"的接口 |
| 差异 | 2 | 和 Game Tests、playtest skill、宿主提示词重叠，只剩独立评审和证据检查是新的 |
| **合计** | **62** | 15 + 12 + 8 + 15 + 8 + 4 |

**结论：需修正（有致命风险）**
- MVP 收窄到两件事：
  1. 回合级证据检查：改了代码，改动之后却没有 `game_use` 截图或快照记录，就提醒。
  2. 只看画面的独立评审：读设计文档里的验收条目，不给评审看代码。
- 不变式交给 Game Tests，提成它的一个 step 类型。
- 下一代必须先做"埋 bug 基准"，给出误报率数据；否则淘汰。

**变异建议**
- 和 P1-12 的"回合后 API 检查"合并成"交付质量门"：回合结束时同时查运行证据、画面和错误 API。
- 和 Game Tests 维护者对齐：通过验收的条目自动导出成回归用例。

### P1-02 数值平衡实验室（balance-lab）

**证据核对**
- E27（强）：balance 是平均浏览量高的标签，也是得分和收藏高的标签。这条成立。
- E13 的"Lack of fun 27 次"讲的是不好玩，不等于数值失衡，引用略有**过度**。
- E41 里"millions of simulated games headless"是单个轶事。
- E93、E95 说明数值驱动的品类命中率较高。这支持"目标用户存在"，不支持"他们需要模拟器"。

**致命问题检查**
- **重复**：不重复。
  - claude-code-game-studios 的 `balance-check` 只是让 Agent 静态读公式，不跑游戏。
  - `simulateRoom` 只是测试底座，确定性时钟和种子都已有（已核实 `game-sdk/src/testing.ts`）。
  - 调参面板只能手调单局。
- **可行**：最大的风险是"从 AI 写的游戏代码里抽出纯逻辑"。规则和渲染混在一起的项目，抽出来的模拟会失真。用 SDK `defineGame` 写的多人规则天然是纯函数，是最稳的切入点。
- **契合**：一般。只覆盖数值驱动的品类。

**评分**

| 维度 | 分 | 理由 |
|---|---|---|
| 频率 | 3 | E27 浏览量高（强），但只覆盖部分品类（E93） |
| 严重度 | 2 | 没有证据说明数值失衡会导致项目放弃或卖不动；E13 讲的是更广的"不好玩" |
| 证据 | 3 | E27 强，E13 间接，E36 弱 |
| 契合 | 3 | 有 Tune 和 `simulateRoom` 可接，但实时、物理类游戏用不上 |
| 可行 | 3 | 没有硬缺口，但抽纯逻辑不可靠 |
| 差异 | 4 | OhMyGame 和插件里都没有批量模拟；Machinations 要另画一遍模型 |
| **合计** | **58** | 15 + 8 + 12 + 9 + 6 + 8 |

**结论：需修正**
- MVP 收窄成两条入口：
  1. 用 SDK `defineGame` 写规则的游戏：直接拿机器人批量跑 `simulateRoom`。
  2. 放置和增量游戏：从 `tuning.json` 和一份经济公式文件，模拟"距下一次升级的等待时间"曲线。
- 不承诺能从任意代码里抽纯逻辑。

**变异建议**
- 和 web-game-studio 的模板约定"模拟核心与渲染分离"，从新项目开局就这么写，比事后抽取可靠。
- 把"疑似问题加种子"的复现入口接到 P1-01 和 Game Tests。

### P1-03 真人试玩回路（playtest-loop）

**证据核对**
- E21（强，定性 n=13）和 E22（强，n=10）支持"难在记录、分析和处理反馈"。
- E24（中）：jam 作品评分中位只有 14 个。这是反馈稀缺的**定量**证据。
- E26（强，官方）：平台已经把"上传后几分钟内拿到真人录像"做成基础设施，说明这个做法有价值。
- E8 的 LORT 是单案例。
- E5 的"首周好评率 91% vs 67%"可以补进来，作为"上线前多试玩"的间接理由。
- 整体没有过度引用。

**致命问题检查**
- **重复**：不重复。已核实社区只有去重后的进入次数、点赞和评论，文档原话说这些数字"do not establish that the game finished loading or a human played it"（`runtime.md` 第 1376–1397 行）。SDK 里没有任何埋点接口。
- **可行**：缺口真实存在，但提案的说法要改。
  - `capabilities.network` 的静态主机列表只限制**插件页面**；插件原生代码不受沙箱限制。
  - 真正的问题是：**发布出去的游戏**要把事件发到哪里，以及隐私合规由谁负责。
  - 宿主在 OhMyGame Cloud 开一个收集接口是最干净的方案。在那之前，MVP 可以要求用户自己填后端，体验较差。
- **契合**：高。"发布成链接"是 OhMyGame 内置的一步，评论读取接口也已公开。
- 没解决的部分：**招人**（E21 第 2 点）。插件不负责把玩家带来。

**评分**

| 维度 | 分 | 理由 |
|---|---|---|
| 频率 | 4 | 试玩是痛点索引第 4 条；E21、E22 是论文，E24 有定量数据 |
| 严重度 | 3 | E13 建议多试玩，E5 好评率差距明显，但没有证据说明缺试玩会导致项目放弃 |
| 证据 | 3 | 论文是小样本定性研究，E24 是计算值，E26 是官方 |
| 契合 | 5 | 正好接在发布链接加 Agent 修复的回路上 |
| 可行 | 3 | 依赖宿主或第三方收集后端，片段上传有成本 |
| 差异 | 4 | GameAnalytics 只出指标，不带片段，也不接 Agent |
| **合计** | **73** | 20 + 12 + 12 + 15 + 6 + 8 |

**结论：保留（需小修）**
- MVP 去掉视频片段和玩法 A/B，只做四样：漏斗、死亡和退出点、无偏问卷、评论和消息聚类。
- 片段和 A/B 留到第二期。
- 向宿主正式提出"已发布游戏的试玩事件收集接口"，并写清数据保留期。

**变异建议**
- 补上"招人"这一半：宿主社区开一个"求试玩"信息流（E24：有网页版的作品拿到的评分约是没有的 5 倍）。
- 和 P1-02 交叉验证：模拟发现的问题，用真人数据确认。

### P1-04 网页上线体检（web-launch-doctor）

**证据核对**
- E53、E56、E62、E82 都是官方规则，有 Cannon Clash 的前后数据（2.4 MB、81% 进入率）。是本代证据最硬的一组。

- E27 的 aspect-ratio（4,483 次浏览）支持屏幕适配需求。

**致命问题检查**
- **重复**：部分重叠。

    - 移动端规则的静态和运行时检查；
    - **局域网真机扫码测试**：已核实宿主没有局域网服务和二维码，多人后端也只监听回环地址。
- **可行**：可以做。
  - `build.*` 钩子只能听，不能拦（已核实）。

**评分**

| 维度 | 分 | 理由 |
|---|---|---|
| 频率 | 4 | OhMyGame 的主要项目类型是网页游戏，上手机、门户、小游戏都会碰到预算问题（E53、E56、E62、E82）；E65 弱 |

| 证据 | 4 | 多份官方规则加 Cannon Clash 定量数据；没有驳回率数据 |
| 契合 | 5 | `build: "web"`、`capabilities.game`、发布菜单都能用上 |
| 可行 | 4 | 没有硬缺口；拦不住发布，ffmpeg 要自带 |
| 差异 | 3 | 和发布对话框的包体信息部分重叠；Lighthouse 不懂游戏素材 |
| **合计** | **81** | 20 + 16 + 16 + 15 + 8 + 6 |

**结论：保留（需修正）**
- 删掉第 6 项"预览设备"。
- 第 1 项要说明和发布对话框的区别：按平台预算，首包和懒加载分开。
- "iOS 内存估算"降级为启发式提示，不当结论。
- 真机扫码测试保留，它是唯一的硬增量。

**变异建议**
- 和 P1-05 共用"目标平台配置"，最好合并成一个"发布前检查"插件。配置至少包括：社区、CrazyGames、Poki、Playables、**微信/抖音主包 4 MB**。
- 微信和抖音的"超 4 MB 自动拆分包"建议放进第二期，它对国内用户价值很大（E82）。

### P1-05 网页门户适配器（portal-adapter）

- **变现低**（E69）：会削弱"值得做"的理由，但不算致命。

**评分**

**变异建议**

### P1-06 商店页与短视频素材（store-kit）

**证据核对**

## 3. 没有被很好覆盖的高频痛点

1. **国内小游戏的变现和分享接入（痛点 7、15、16）**：本代最大的漏项。
   - 证据：小程序游戏 535 亿元，广告占 31.89%（E72）；微信 IAA 月活 4 亿，70% 的用户只玩 IAA（E74）；IAA 分成激励最高约 90%（E76）；社交渠道注册占比 30–50%，部分 IAA 游戏 80% 以上的收入来自社交渠道用户（E75）；抖音 IAA 在投产品 +75%（E78）。
   - 现状：wechat-minigame 和 douyin-minigame 只管构建和上传，没有激励视频、插屏、分享的统一接口和规则检查。
   - 建议：做 P1-05 的国内版，统一接口加模拟广告层加规则检查（激励视频的发奖时机、分享卡片）。在 OhMyGame 用户里，它可能比 P1-05 更有价值。
2. **发现性，玩家侧传播（痛点 1）**：现有候选只做开发者侧的素材。
   - 证据：Next Fest 突破者靠玩家剪辑和创作者传播（E8：YAPYAP 一周 50K 条 Medal 剪辑）；主播是 39% 开发者的获客渠道（E9）；网页玩家"more like TikTok viewers"（E54）。
   - 建议：给游戏加"一键回放、截最后 N 秒、分享"的 SDK 组件，再加一个主播模式。目前没有候选覆盖这一块。
3. **试玩招募（痛点 4 的另一半）**：P1-03 只让每个玩家的数据更有用，不负责找人。
   - 证据：有网页版的 jam 作品，评分约是没有的 5 倍（E24）；E21 第 2 点讲的就是招人难。
   - 建议：宿主社区开"求试玩"信息流，或者 jam 互评。
4. **设计愿景不清、不好玩，需要快速原型（痛点 3）**：只有 P1-14 的意图卡和 P1-03 的 A/B 沾边。
   - 证据：论文作者建议多做原型（E13）；67% 的原型期不超过 3 个月，52% 靠做小项目降风险（E20）。
   - 建议：做"同一个核心玩法的 2–3 个变体并排试玩"的原型擂台，把 Agent 低成本出变体的能力用起来。
5. **英文化和本地化（E55 硬门槛，E104）**：没有候选。
   - 证据：CrazyGames 没有英文直接驳回（E55）；45% 用 AI 做本地化（E36，厂商）。
   - 建议：抽取字符串、翻译，再用 `capabilities.game` 截图检查文字溢出。这和 OhMyGame 的流程很契合；"哪些语言回报高"没有数据，但"至少要有英文"是硬规则。
6. **音频（痛点 9 的一半）**：证据空白，暂不提，同意生成者的判断。
7. **iOS Safari 的内存和 WebGL 崩溃（痛点 8）**：P1-04 的真机扫码测试能部分覆盖，内存估算没有依据。

## 4. 宿主缺口核对

| # | 提案说的缺口 | 核对结果 | 影响多大 |
|---|---|---|---|
| 1 | `turn.completed` 只能弹 toast，不能退回给 Agent（P1-01、P1-14） | **属实**。`plugins.md`：除 `image.beforeGenerate` 和 `tool.beforeCall` 外，钩子都只能听，可返回 `{notice, tone}` | 中。影响"证据检查"能否强制执行；`sessions.send` 权限过大，不能拿来代替 |
| 2 | 模型调用每插件 3 并发、每分钟 30 次（P1-01） | **属实** | 中。逐帧评审必须抽样 |
| 3 | 插件会话能否调用测试桥的 `step` 和 `snapshot`（P1-01） | **文档没写明**。`actTogether` 会返回每个玩家的 snapshot，可以推断能用，`step` 要实测；原生项目类型的运行时明确"no bridge" | 低 |
| 4 | `image.beforeGenerate` 不能加参考图（P1-09） | **属实**："It can't add or remove reference images" | **高**。是风格一致性的主要手段 |
| 5 | Check pixel art 没开放给插件（P1-09） | **属实**，但影响小。它只是 daemon 的画布路由（`canvas-routes.ts`），不在插件 API 里；算法用 MIT 许可、规模小 | 低 |
| 6 | `capabilities.network` 的主机写死，用户后端没法动态声明（P1-03） | **部分属实**。只限制页面的 `net.fetch` 和 MCP；原生代码不受沙箱限制。真正的缺口是已发布游戏的数据收集后端和隐私合规 | 中到高。P1-03 MVP 的前提 |
| 7 | 会话拿不到每个请求的字节数和耗时（P1-04） | **属实**。只返回 failed-request 数据 | 低。静态分析加真机回传可以代替 |
| 8 | `build.*` 钩子拦不住发布（P1-04、P1-11） | **属实** | 中。所有"发布门禁"类插件只能提醒 |
| 9 | 原生 Agent 的文件操作绕过 `tool.beforeCall`（P1-12） | **属实**。文档原话："Native coding agents' own file/shell tools … are outside this boundary" | **高**。直接导致 P1-12 核心失效 |
| 10 | 没有"用户消息到达、Agent 开始前"的钩子（P1-14） | **基本属实**。只有插件项目类型的 `ready` 检查能在提示前运行 | 低 |
| 11 | 插件之间不能互相调用（P1-14） | **属实**，而且是明确"不做"的设计（`plugin-plan.zh-CN.md` 第 42 行） | 中。这是合并发布检查类插件的直接理由 |
| 12 | SOCKS5 代理只有开和关，没有延迟参数（P1-15） | **属实**。每个窗口有独立的代理（`src/desktop/playtest-network.ts`），只有 `setOnline` | 中。宿主补起来改动小，补完 P1-15 大半就没了 |
| 13 | 本地多人后端只监听回环地址，没法局域网多真机（P1-15、P1-04） | **属实**（`multiplayer.md` 第 110 行）；宿主没有局域网静态服务和二维码 | 中。P1-04 和 P1-15 的真机测试都依赖它 |
| 14 | OhMyGame SDK 不能按构建目标切换后端（P1-05） | **属实**。SDK 里没有门户适配层 | 中。门户会拦外部请求，可能直接白屏 |
| 15 | 插件录屏单段最长 60 秒（P1-06） | **属实**（`plugins.md` 第 486 行） | 低 |
| 16 | 插件不能直接调用图像、音频生成（P1-06、P1-08） | **属实**。`capabilities.models` 只有语言模型 | 中 |
| 17 | **新发现**：宿主的 ffmpeg 没开放给插件 | 宿主带 `ffmpeg-static`，只给自己的媒体工具用；插件 API 里没有。提案说"复用宿主 ffmpeg"缺少依据 | 中。P1-04、P1-06、P1-08 要自己下载 ffmpeg（GPL，体积大，插件包上限 50 MB） |
| 18 | **新发现**：没有"已发布游戏的试玩和行为数据" | 社区只有去重后的进入次数、点赞和评论，文档原话说这些数字"do not establish that the game finished loading or a human played it" | 高。P1-03、P1-05、P1-14 的效果都没法衡量 |

**最值得向宿主提的三个缺口**
1. 已发布游戏的试玩事件收集接口（#6、#18）：P1-03 的前提，也能用来衡量 P1-14 的效果。
2. `image.beforeGenerate` 允许追加项目内的参考图（#4）。
3. 游戏会话的网络条件参数，加上局域网预览开关（#12、#13）。

另外，开放 ffmpeg 路径（#17）成本很低，能让三个候选直接受益。
